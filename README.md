## Введение

В данной работе реализована и исследована операция параллельной редукции одномерного массива: вычисление суммы всех элементов и нахождение максимального значения. Цель — сравнить последовательный и параллельные подходы на CPU и GPU, проанализировать производительность и ускорение.

В рамках работы реализованы три версии алгоритма:

1. Последовательная версия на CPU — классический проход по массиву с накоплением суммы и обновлением максимума в одном потоке.
2. Параллельная версия на CPU с OpenMP — автоматическое разбиение цикла между потоками процессора с использованием директив `reduction(+:s)` и `reduction(max:m)`.
3. Параллельная версия на GPU с CUDA — reduction kernel с использованием shared memory и дерева редукции внутри блоков, с финальным объединением частичных результатов на CPU.

Редукция — фундаментальная операция параллельных вычислений. Она лежит в основе таких алгоритмов, как вычисление статистик, нормализация данных, сортировка и физическое моделирование. Несмотря на кажущуюся последовательную природу, операция хорошо параллелится благодаря ассоциативности: порядок группировки не влияет на результат.

## Последовательная версия (CPU)

Последовательная реализация служит эталоном для проверки корректности и базой для расчёта ускорения. Алгоритм имеет сложность `O(N)` и минимальные накладные расходы — один проход по массиву, два аккумулятора (`long long` для суммы, `int` для максимума).

Для малых массивов (100K) это самый быстрый вариант: **0.125 мс**. Никаких затрат на создание потоков, копирование памяти или синхронизацию. Однако при росте N время растёт линейно, и на 10M элементов уже **14.97 мс** — здесь последовательный подход проигрывает.


## Параллельная версия CPU (OpenMP)

OpenMP-версия использует директивы:
- `reduction(+:s)` для суммы
- `reduction(max:m)` для максимума

Компилятор автоматически разбивает цикл между доступными ядрами CPU (в Colab обычно 2 ядра).

На 100K элементов OpenMP медленнее последовательной версии (0.185 мс vs 0.125 мс) — накладные расходы на создание и управление потоками превышают выигрыш.  
На 1M элементов OpenMP становится быстрее (ускорение ~1.22x).  
На 10M элементов ускорение достигает ~1.33x.

Это типичная ситуация для CPU-параллелизма в Google Colab: малое число ядер и высокая стоимость синхронизации.


## Параллельная версия GPU (CUDA)

CUDA-реализация использует один kernel, который одновременно вычисляет сумму и максимум. Внутри каждого блока (256 потоков) данные загружаются в shared memory, затем выполняется дерево редукции. Частичные результаты копируются на CPU для финального объединения.

Ключевое наблюдение — разница между временем ядра и полным временем выполнения.

Для 100K элементов:
- kernel: 0.024 мс (ускорение ~5.2x)
- total: 0.197 мс (медленнее CPU)

Для 10M элементов:
- kernel: 1.014 мс (ускорение ~14.8x)
- total: 9.78 мс (ускорение ~1.53x)

Это демонстрирует, что при увеличении размера массива доля полезных вычислений растёт, а накладные расходы на копирование становятся менее критичными.
